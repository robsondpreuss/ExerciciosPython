01

Por que controle de versão?

Conceito

Você já criou projeto_final_v2_AGORA_VAI_definitivo.py? Todo mundo já. O Git acaba com isso: ele guarda TODAS as versões do seu projeto numa linha do tempo de commits (fotografias do código). Você viaja entre versões, compara mudanças, e — em time — várias pessoas trabalham no mesmo projeto sem se atropelar.

Instale o Git (git-scm.com; no Windows o instalador padrão resolve) e configure seu nome uma única vez:

terminal
git config --global user.name "Seu Nome"
git config --global user.email "seu@email.com"
EX 01

git init: nasce um repositório 🌱

⭐ básico
🎯 Objetivo

Transformar a pasta do projeto num repositório Git.

🧭 Passo a passo
  1. Na pasta do seu projeto (ex.: a API da Tua Caneca), rode git init
  2. Rode git status e leia com calma: ele lista os arquivos "untracked" (ainda fora da linha do tempo)
terminal
$ git init
Initialized empty Git repository in .../tua_caneca/.git/

$ git status
On branch main
Untracked files:
  api.py
  db.py
  test_api.py
✅ Saída esperada
terminal
(repositório criado — a pasta oculta .git é a "máquina do tempo")
💡 O git status é seu GPS
Sempre que estiver perdido no Git, rode git status: ele diz em que branch você está, o que mudou e até sugere o próximo comando. É o comando mais digitado do mundo — use sem moderação.
02

add e commit: salvando versões

Conceito

O ciclo básico do Git tem dois passos: o git add escolhe as mudanças que entram na próxima "fotografia", e o git commit tira a foto com uma etiqueta (a mensagem). Repita esse ciclo a cada avanço pequeno — commits frequentes e focados são a marca de quem versiona bem.

EX 02

add + commit: a primeira fotografia 📸

⭐⭐ médio
🎯 Objetivo

Salvar a primeira versão do projeto na linha do tempo.

🧭 Passo a passo
  1. O fluxo tem 2 passos: git add ESCOLHE o que entra na foto; git commit TIRA a foto
  2. Adicione tudo: git add .
  3. Commite com mensagem: git commit -m "Primeira versao da API Tua Caneca"
terminal
$ git add .
$ git commit -m "Primeira versao da API Tua Caneca"
[main (root-commit) a1b2c3d] Primeira versao da API Tua Caneca
 3 files changed, 180 insertions(+)
✅ Saída esperada
terminal
(primeiro commit feito — a versão está eternizada)
💡 Por que dois passos?
O add existe para você MONTAR a foto: dá para commitar só um arquivo mexido e deixar outro para o próximo commit. Pense no add como "colocar na caixinha" e no commit como "lacrar a caixinha com uma etiqueta". A etiqueta (mensagem) importa — já já falamos dela.
EX 03

A arte da mensagem de commit ✍️

⭐⭐ médio
🎯 Objetivo

Escrever mensagens que o seu "eu do futuro" agradece.

🧭 Passo a passo
  1. Compare os dois históricos abaixo — qual deles ajuda a achar onde o bug do desconto entrou?
  2. Regra prática: a mensagem completa a frase "Este commit... [adiciona validação no POST]"
historico_ruim.txt
git log --oneline
9f8e7d6 arrumei
5c4b3a2 mudancas
1a2b3c4 agora vai
d4e5f6a coisas
historico_bom.txt
git log --oneline
9f8e7d6 Corrige calculo do desconto acima de 100
5c4b3a2 Adiciona validacao de nome no POST /api/produtos
1a2b3c4 Protege rotas de escrita com @token_required
d4e5f6a Cria endpoints GET de produtos
💡 Commits contam a história
Um bom histórico é a NARRATIVA do projeto: dá para entender a evolução sem abrir código. Convenção comum: verbo no presente ("Adiciona", "Corrige", "Remove") + o quê + onde. Times sérios recusam commits com mensagem vaga — e recrutadores olham seu histórico no GitHub!
03

Viajando no tempo: log, diff e restore

Conceito

Com commits acumulados, o Git vira sua máquina do tempo: git log mostra a linha do tempo, git diff mostra o que mudou desde a última foto, e git restore desfaz bagunça.

EX 04

log e diff: o que mudou? 🔍

⭐⭐ médio
🎯 Objetivo

Inspecionar o histórico e as mudanças pendentes.

🧭 Passo a passo
  1. Mexa em algum arquivo (mude uma linha da API)
  2. Rode git diff: as linhas removidas aparecem com -, as novas com +
  3. Rode git log --oneline para ver a linha do tempo resumida
terminal
$ git diff
- return jsonify({"ok": True})
+ return jsonify({"ok": True, "id": novo_id}), 201

$ git log --oneline
5c4b3a2 Adiciona validacao de nome no POST
1a2b3c4 Primeira versao da API
✅ Saída esperada
terminal
(você enxerga exatamente o que mudou antes de commitar)
💡 O diff antes do commit
Hábito de ouro: rodar git diff ANTES de todo commit, para conferir o que vai na foto. Quantas vezes um print de debug esquecido foi parar em produção porque ninguém olhou o diff... Não seja essa pessoa. 😄
EX 05

restore: o botão de desfazer 🧯

⭐⭐ médio
🎯 Objetivo

Recuperar um arquivo depois de uma bagunça.

🧭 Passo a passo
  1. Estrague um arquivo de propósito (apague metade do api.py e salve!)
  2. Respire: git restore api.py
  3. Abra o arquivo: ele voltou à última foto. Crise cancelada
✅ Saída esperada
terminal
(o arquivo restaurado, idêntico ao último commit)
💡 A rede embaixo do trapézio
Esse é o momento em que o Git muda sua vida: errar deixa de ser perigoso. Refatorações ousadas, experimentos, testes destrutivos — tudo fica seguro, porque a última versão commitada está a um git restore de distância. Commite cedo, commite sempre.
04

.gitignore: o segurança do repositório

Conceito

NEM TUDO deve entrar na linha do tempo: senhas (.env!), lixo gerado (__pycache__), o banco local. O arquivo .gitignore lista o que o Git deve fingir que não existe. Esta é uma lição de segurança séria: segredo commitado é segredo vazado.

EX 06

Montando o .gitignore 🛡️

⭐⭐ médio
🎯 Objetivo

Proteger segredos e excluir lixo do repositório.

🧭 Passo a passo
  1. Crie o arquivo .gitignore na raiz do projeto com o conteúdo abaixo
  2. Rode git status: os itens listados SOMEM da lista de untracked
  3. Commite o próprio .gitignore (ele sim, vai para o repositório!)
.gitignore
# segredos — NUNCA no repositorio!
.env

# lixo do Python
__pycache__/
*.pyc

# ambiente virtual (Semana 34)
venv/

# banco local de testes
*.db
✅ Saída esperada
terminal
(git status limpo — os segredos invisíveis para o Git)
💡 A regra que salva carreiras
Robôs varrem o GitHub 24h por dia atrás de senhas e chaves commitadas — um .env público é sequestrado em MINUTOS (lembra da lição da Semana 24?). E atenção: o Git guarda o HISTÓRICO — remover o arquivo depois não apaga as versões antigas! Por isso o .gitignore vem PRIMEIRO, antes do primeiro commit. Grave isso. 🔐
05

GitHub: publicando (e as branches)

Conceito

O Git guarda a história na SUA máquina; o GitHub a hospeda na nuvem — backup, vitrine e ponto de colaboração. O fluxo: criar o repositório no site, conectar com git remote add, enviar com git push.

EX 07

Subindo para o GitHub ☁️

⭐⭐ médio
🎯 Objetivo

Publicar seu repositório local no GitHub.

🧭 Passo a passo
  1. No github.com: New repository → nome (ex.: tua-caneca-api) → SEM inicializar com nada → Create
  2. Conecte e envie com os comandos que o próprio GitHub mostra:
terminal
git remote add origin https://github.com/SEU-USUARIO/tua-caneca-api.git
git branch -M main
git push -u origin main
✅ Saída esperada
terminal
(atualize a página do GitHub: seu código está lá, com todo o histórico!)
💡 remote, origin, push
remote = um endereço de repositório na nuvem; origin = o apelido padrão dele; push = "empurrar" seus commits para lá. O caminho de volta é o git clone URL — que baixa qualquer repositório público para sua máquina (ótimo para estudar código dos outros!).
EX 08

Branches: o universo paralelo 🌿

⭐⭐⭐ desafio
🎯 Objetivo

Desenvolver uma novidade sem tocar na versão que funciona.

🧭 Passo a passo
  1. Crie e entre numa branch: git switch -c relatorio-clientes
  2. Faça commits nela (mexa num arquivo, add, commit) — a main fica intacta!
  3. Volte para a main (git switch main) e traga a novidade: git merge relatorio-clientes
terminal
$ git switch -c relatorio-clientes
Switched to a new branch 'relatorio-clientes'
$ git add . && git commit -m "Adiciona relatorio por cliente"
$ git switch main
$ git merge relatorio-clientes
Fast-forward
 api.py | 12 ++++++++++++
✅ Saída esperada
terminal
(a novidade desenvolvida em paralelo e trazida para a main)
💡 Como os times trabalham
Em empresas, a main é sagrada (é o que está no ar!) e TODA mudança nasce numa branch — que só entra via merge depois de revisão e testes (a suíte da Semana 32!). Você acabou de experimentar o fluxo de trabalho de 99% dos times de software do planeta.

terminal
(dois READMEs que explicam, ensinam a rodar e vendem o projeto)
💡 O produto é você
Um bom README responde em 30 segundos: o que faz? como rodo? o autor sabe o que está fazendo? Projetos com README caprichado passam a impressão de cuidado — a mesma que um portfólio bem montado passa num processo seletivo. Você construiu 33 semanas de conteúdo; agora aprenda a APRESENTÁ-LO. 🎯
