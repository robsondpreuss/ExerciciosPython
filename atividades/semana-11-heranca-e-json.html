01

Por que autenticar (e o pecado da senha em texto puro)

Conceito

Sua API REST da Semana 27 está ABERTA: qualquer um pode criar, editar e apagar produtos. Sistemas reais precisam saber quem está fazendo cada coisa — isso é autenticação. E o primeiro mandamento: senha JAMAIS se guarda em texto puro.

Por quê? Se o banco vazar (acontece o tempo todo), todas as senhas estariam expostas. A solução é guardar um hash: uma "impressão digital" irreversível da senha. Dá para verificar se a senha digitada bate com o hash, mas é impossível descobrir a senha a partir dele.

EX 01

O perigo da senha em texto puro 🚨

⭐ básico
🎯 Objetivo

Entender por que guardar senhas como texto é um desastre.

Imagine uma tabela de usuários guardando a senha assim:

PERIGOSO.txt
usuario  | senha
---------|--------
robson   | tuacaneca123
ana      | euamocafe
🧭 Passo a passo
  1. Reflita: se um invasor copiar essa tabela, o que ele tem? (Resposta: TUDO — todas as senhas, na cara.)
  2. Pior: muita gente repete a senha em vários sites. Vazou a sua, vazou o e-mail, o banco...
  3. A solução (próximo exercício): guardar o HASH, não a senha
💡 Casos reais
Vazamentos de bancos de dados com senhas em texto puro já expuseram MILHÕES de contas e renderam processos milionários. Guardar hash em vez de senha não é "boa prática opcional" — é obrigação ética e legal (a LGPD, no Brasil, cobra isso). Você está aprendendo a fazer certo desde o começo.
EX 02

Hash de senha: o jeito certo 🔒

⭐⭐ médio
🎯 Objetivo

Gerar e verificar um hash de senha — sem instalar nada novo.

🧭 Passo a passo
  1. O Flask já traz o werkzeug.security — sem instalação extra!
  2. Importe generate_password_hash e check_password_hash
  3. Gere o hash de uma senha e depois verifique se uma tentativa bate
ex02_hash.py
from werkzeug.security import generate_password_hash, check_password_hash

senha = "tuacaneca123"

# guardar ISTO no banco (nunca a senha!):
hash_senha = generate_password_hash(senha)
print("Hash:", hash_senha[:40], "...")

# na hora do login, verifica:
print(check_password_hash(hash_senha, "tuacaneca123"))  # True (senha certa)
print(check_password_hash(hash_senha, "errada"))         # False
✅ Saída esperada
terminal
Hash: scrypt:32768:8:1$abc123... ...
True
False
💡 Mão única
O generate_password_hash embaralha a senha de um jeito IRREVERSÍVEL (e ainda adiciona um "sal" aleatório, então duas pessoas com a mesma senha têm hashes diferentes!). O check_password_hash verifica sem nunca "desembaralhar". É matemática a seu favor: fácil de verificar, impossível de reverter.

EX 03

Tabela de usuários + cadastro

⭐⭐ médio
🎯 Objetivo

Criar a tabela usuarios e o endpoint de cadastro com hash.

🧭 Passo a passo
  1. No DBeaver (ou por código), crie a tabela usuarios (id, usuario único, senha_hash)
  2. Endpoint POST /api/cadastro: recebe usuario e senha no JSON
  3. Gere o hash com generate_password_hash e faça o INSERT (com %s!)
  4. Nunca guarde a senha — só o hash
cadastro.sql
CREATE TABLE IF NOT EXISTS usuarios (
    id INT AUTO_INCREMENT PRIMARY KEY,
    usuario VARCHAR(50) UNIQUE,
    senha_hash VARCHAR(255)
);
ex03_cadastro.py
from flask import Flask, jsonify, request
from werkzeug.security import generate_password_hash
from db import conectar   # Semana 26

app = Flask(__name__)

@app.route("/api/cadastro", methods=["POST"])
def cadastro():
    dados = request.get_json()
    usuario = dados.get("usuario", "").strip()
    senha = dados.get("senha", "")
    if not usuario or not senha:
        return jsonify({"erro": "usuario e senha obrigatórios"}), 400

    hash_senha = generate_password_hash(senha)
    con = conectar(); cur = con.cursor()
    cur.execute("INSERT INTO usuarios (usuario, senha_hash) VALUES (%s, %s)",
                (usuario, hash_senha))
    con.commit(); con.close()
    return jsonify({"ok": True, "usuario": usuario}), 201

app.run(debug=True)
✅ Exemplo
terminal
POST /api/cadastro {"usuario": "robson", "senha": "..."} -> 201
💡 VARCHAR(255) para o hash
O hash é uma string longa — por isso VARCHAR(255). E o UNIQUE no usuário impede dois cadastros com o mesmo nome (o banco recusa sozinho). Confira no DBeaver: a coluna senha_hash guarda aquele embaralhado, nunca a senha legível. 🔒
03

Login: verificando a senha e emitindo o JWT

Conceito

O login faz duas coisas: confere a senha (com check_password_hash) e, se bater, devolve um JWT (JSON Web Token) — um "crachá digital" assinado que o cliente vai apresentar nas próximas requisições. Usamos a biblioteca PyJWT (pip install pyjwt).

EX 04

O endpoint de login 🎫

⭐⭐⭐ desafio
🎯 Objetivo

Verificar a senha e gerar um token JWT assinado.

🧭 Passo a passo
  1. Busque o usuário no banco; se não existe ou a senha não bate (check_password_hash), retorne 401
  2. Se bate, gere o token com jwt.encode: um payload com o usuário e uma EXPIRAÇÃO (exp)
  3. A chave secreta vem do ambiente (JWT_SECRET) — nunca no código!
  4. Devolva o token no JSON
ex04_login.py
import os
import jwt
from datetime import datetime, timedelta, timezone
from flask import Flask, jsonify, request
from werkzeug.security import check_password_hash
from db import conectar

app = Flask(__name__)
SEGREDO = os.environ.get("JWT_SECRET", "troque-este-segredo")

@app.route("/api/login", methods=["POST"])
def login():
    dados = request.get_json()
    usuario = dados.get("usuario", "")
    senha = dados.get("senha", "")

    con = conectar(); cur = con.cursor()
    cur.execute("SELECT senha_hash FROM usuarios WHERE usuario = %s", (usuario,))
    r = cur.fetchone(); con.close()

    if r is None or not check_password_hash(r[0], senha):
        return jsonify({"erro": "usuario ou senha invalidos"}), 401

    token = jwt.encode(
        {"usuario": usuario,
         "exp": datetime.now(timezone.utc) + timedelta(hours=2)},
        SEGREDO, algorithm="HS256")
    return jsonify({"token": token})

app.run(debug=True)
✅ Exemplo
terminal
POST /api/login {"usuario": "robson", "senha": "..."}
-> {"token": "eyJhbGciOiJIUzI1NiIs..."}   (ou 401 se errado)
💡 O que tem no token?
O jwt.encode embala o payload (quem é o usuário + quando expira) e ASSINA com o segredo. Qualquer alteração no token quebra a assinatura. O exp faz o token "vencer" em 2 horas — segurança extra. E note o 401 genérico ("usuario OU senha inválidos"): nunca diga QUAL está errado, para não ajudar invasores. 🕵️
04

Protegendo rotas com o token

Conceito

Agora o cliente envia o token a cada requisição, no cabeçalho Authorization: Bearer <token>. A rota protegida LÊ esse cabeçalho, valida o token com jwt.decode e só então executa. Token inválido ou ausente → 401.

EX 05

Anatomia do JWT 🔬

⭐⭐ médio
🎯 Objetivo

Espiar o que há dentro de um token e validá-lo.

🧭 Passo a passo
  1. Um JWT tem 3 partes separadas por ponto: header.payload.signature
  2. Use jwt.decode (com o segredo e o algoritmo) para LER o payload de volta
  3. Veja que o usuário e a expiração estão lá dentro
ex05_decode.py
import os
import jwt

SEGREDO = os.environ.get("JWT_SECRET", "troque-este-segredo")

# token recebido (ex. veio do login)
token = "COLE_AQUI_UM_TOKEN_DO_LOGIN"

dados = jwt.decode(token, SEGREDO, algorithms=["HS256"])
print("Payload:", dados)
print("Usuário do token:", dados["usuario"])
✅ Exemplo
terminal
Payload: {'usuario': 'robson', 'exp': 1751300000}
Usuário do token: robson
💡 Assinado, não criptografado
O payload do JWT NÃO é secreto — qualquer um consegue ler o conteúdo (em jwt.io dá para colar e ver!). O que ele garante é AUTENTICIDADE: como é assinado com o seu segredo, ninguém consegue FORJAR um token válido. Por isso: nunca coloque senha ou dado sensível dentro do payload!
EX 06

A rota protegida 🚪

⭐⭐⭐ desafio
🎯 Objetivo

Exigir um token válido para acessar uma rota.

🧭 Passo a passo
  1. Leia o cabeçalho: request.headers.get("Authorization")
  2. Extraia o token depois do "Bearer "
  3. Valide com jwt.decode; se falhar, retorne 401
  4. Se passar, execute normalmente (você até sabe QUEM é, pelo payload!)
✅ Exemplo
terminal
GET /api/protegido  (com Bearer token válido) -> {"mensagem": "Olá, robson!"}
GET /api/protegido  (sem token)              -> 401

Só abra depois de tentar!

solucao_ex06.py
import os, jwt
from flask import Flask, jsonify, request

app = Flask(__name__)
SEGREDO = os.environ.get("JWT_SECRET", "troque-este-segredo")

@app.route("/api/protegido")
def protegido():
    cabecalho = request.headers.get("Authorization", "")
    if not cabecalho.startswith("Bearer "):
        return jsonify({"erro": "token ausente"}), 401

    token = cabecalho.split(" ")[1]
    try:
        dados = jwt.decode(token, SEGREDO, algorithms=["HS256"])
    except jwt.InvalidTokenError:
        return jsonify({"erro": "token invalido"}), 401

    return jsonify({"mensagem": f"Olá, {dados['usuario']}!"})

app.run(debug=True)
EX 07

O decorator @token_required ♻️

⭐⭐⭐ desafio
🎯 Objetivo

Empacotar a verificação num decorator reutilizável — DRY para a segurança.

🧭 Passo a passo
  1. Imagine repetir aquela verificação em 10 rotas... melhor criar um @token_required
  2. O decorator (pesquise "decorator Python"!) faz a checagem ANTES da rota e passa o usuário adiante
  3. Aí cada rota protegida ganha só uma linha: o @token_required em cima dela
✅ Saída esperada
terminal
(uma única verificação, reaproveitada em todas as rotas protegidas)
💡 DRY na segurança
Lembra do princípio "não se repita" (Semana 6)? Um decorator de autenticação centraliza a regra de segurança num lugar só. Se você mudar a forma de validar, muda UMA função e todas as rotas protegidas acompanham. É o padrão profissional para proteger APIs.
🔑 Ver solução

Só abra depois de tentar!

auth.py
import os, jwt
from functools import wraps
from flask import jsonify, request

SEGREDO = os.environ.get("JWT_SECRET", "troque-este-segredo")

def token_required(f):
    @wraps(f)
    def wrapper(*args, **kwargs):
        cabecalho = request.headers.get("Authorization", "")
        if not cabecalho.startswith("Bearer "):
            return jsonify({"erro": "token ausente"}), 401
        token = cabecalho.split(" ")[1]
        try:
            dados = jwt.decode(token, SEGREDO, algorithms=["HS256"])
        except jwt.ExpiredSignatureError:
            return jsonify({"erro": "token expirado"}), 401
        except jwt.InvalidTokenError:
            return jsonify({"erro": "token invalido"}), 401
        # passa o usuário logado para a rota
        return f(usuario_logado=dados["usuario"], *args, **kwargs)
    return wrapper

# uso:
# @app.route("/api/produtos", methods=["POST"])
# @token_required
# def criar(usuario_logado):
#     ...
05

Os erros de autenticação (401)

Conceito

Três coisas podem dar errado com um token, e todas respondem 401 (Unauthorized): o token pode estar ausente, inválido (adulterado ou com segredo errado) ou expirado (passou das 2h). O PyJWT tem exceções específicas para cada caso.

EX 08

Tratando token ausente, inválido e expirado

⭐⭐ médio
🎯 Objetivo

Responder com a mensagem certa para cada falha de token.

🧭 Passo a passo
  1. Sem cabeçalho Authorization → "token ausente" (401)
  2. jwt.ExpiredSignatureError → "token expirado" (401)
  3. jwt.InvalidTokenError → "token inválido" (401)
  4. Mensagens claras ajudam o frontend a reagir (ex.: token expirado → pedir login de novo)
✅ Comportamento esperado
terminal
sem token      -> 401 {"erro": "token ausente"}
token mexido   -> 401 {"erro": "token invalido"}
token vencido  -> 401 {"erro": "token expirado"}
💡 Por que distinguir?
O frontend (Semana 29) USA essas mensagens: "token expirado" pode disparar um relogin automático; "token inválido" indica adulteração (logout imediato). Tratar cada caso é o que torna a experiência de login fluida e segura. Note que ExpiredSignatureError é um tipo de InvalidTokenError — por isso o expirado vem PRIMEIRO no except (Semana 7!).

teste_protegido.py
import requests

BASE = "http://localhost:5000/api"

# 1) Tenta criar SEM token -> deve dar 401
r = requests.post(f"{BASE}/produtos",
                  json={"nome": "x", "preco": 1, "estoque": 1}, timeout=5)
print("Sem token:", r.status_code)   # 401

# 2) Faz login -> recebe token
r = requests.post(f"{BASE}/login",
                  json={"usuario": "robson", "senha": "tuacaneca123"}, timeout=5)
token = r.json()["token"]

# 3) Cria COM token no cabeçalho -> deve dar 201
headers = {"Authorization": f"Bearer {token}"}
r = requests.post(f"{BASE}/produtos", headers=headers,
                  json={"nome": "caneca nova", "preco": 30, "estoque": 5}, timeout=5)
print("Com token:", r.status_code)   # 201
EX 10

Projeto bônus: /me e o conceito de logout 🚪

⭐⭐⭐ desafio
🎯 Objetivo

Criar uma rota de perfil e entender por que logout no JWT é diferente (sem código pronto!).

🧭 Roteiro
  1. Rota GET /api/me protegida: devolve os dados do usuário logado (pegando do token)
  2. Pesquise: por que, com JWT, o "logout" acontece no CLIENTE (que descarta o token), e não no servidor?
  3. Reflita sobre "stateless": o servidor não guarda sessão — cada requisição se prova sozinha pelo token
✅ Exemplo
terminal
GET /api/me (com token) -> {"usuario": "robson"}
💡 Stateless: a chave do REST
APIs REST são "stateless": o servidor NÃO guarda quem está logado — cada requisição carrega seu próprio token como prova. Por isso o logout é o cliente simplesmente JOGAR FORA o token (Semana 29 fará isso). Essa ausência de "memória de sessão" é o que permite a uma API atender milhões de clientes sem se atrapalhar. Conceito poderoso — e você acabou de dominá-lo. 🧠
