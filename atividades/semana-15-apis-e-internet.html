01

requirements.txt: a lista de ingredientes

Conceito

Seu projeto usa Flask, PyMySQL, PyJWT, flask-cors, pytest... Se alguém clonar seu repositório (Semana 33), como saberá o que instalar? O requirements.txt é a lista de ingredientes: o pip a gera e a consome automaticamente.

EX 01

Congelando as dependências 🧊

⭐⭐ médio
🎯 Objetivo

Gerar o requirements.txt do seu projeto.

🧭 Passo a passo
  1. Na pasta do projeto: pip freeze > requirements.txt
  2. Abra o arquivo: cada linha é pacote==versão
  3. Commite-o (Semana 33) — ele faz parte do projeto!
requirements.txt
Flask==3.0.3
flask-cors==4.0.1
PyJWT==2.9.0
PyMySQL==1.1.1
pytest==8.3.3
✅ Saída esperada
terminal
(o arquivo gerado, com as versões exatas do seu ambiente)
💡 Por que a versão exata?
O == congela a versão TESTADA. Sem isso, quem instalar amanhã pode receber uma versão nova com mudanças que quebram seu código ("funciona na minha máquina" nasce aí). Versões pinadas = comportamento reproduzível em qualquer lugar.
EX 02

Instalando do zero com -r

⭐⭐ médio
🎯 Objetivo

Viver a experiência de quem clona o seu projeto.

🧭 Passo a passo
  1. O comando do outro lado: pip install -r requirements.txt
  2. O pip lê a lista e instala tudo, nas versões exatas
  3. Junte as peças: git clone + pip install -r = projeto rodando em qualquer máquina em 2 comandos
✅ Saída esperada

Collecting Flask==3.0.3 ...

💡 O README agradece
Lembra do "como rodar" do README (Semana 33)? Agora ele fica limpo: clone, instale com -r, configure o .env (Parte 3), rode. Quatro linhas que funcionam para QUALQUER pessoa — inclusive o recrutador testando seu projeto.
02

venv: uma caixa de ferramentas por projeto

Conceito

Problema clássico: o projeto A precisa do Flask 2, o projeto B do Flask 3 — e o pip instala tudo no mesmo lugar! O ambiente virtual (venv) resolve: cada projeto ganha sua própria "caixa" de pacotes, isolada das outras.

EX 03

Criando e ativando o venv 📦

⭐⭐ médio
🎯 Objetivo

Isolar as dependências do projeto num ambiente próprio.

🧭 Passo a passo
  1. Na pasta do projeto: python -m venv venv (cria a pasta venv/)
  2. Ative: Windows venv\Scripts\activate · Linux/Mac source venv/bin/activate
  3. O prompt ganha o prefixo (venv) — os pip install agora vão para a caixa do projeto
  4. E lembre: venv/ já está no seu .gitignore (Semana 33)!
terminal
$ python -m venv venv
$ source venv/bin/activate      # (ou venv\Scripts\activate no Windows)
(venv) $ pip install -r requirements.txt
(venv) $ python api.py
✅ Saída esperada
terminal
(o projeto rodando com SUA caixa de pacotes, isolada do resto)
💡 O ritual profissional
A sequência clone → venv → activate → install -r → rodar é o "bom dia" de todo dev ao pegar um projeto novo. O venv não sobe para o Git (é pesado e recriável); o requirements.txt é a receita para reconstruí-lo em segundos. Caixa descartável, receita eterna.
03

.env: a configuração fora do código

Conceito

Suas credenciais já vivem em variáveis de ambiente (Semanas 24, 26, 28) — mas configurá-las na mão toda vez cansa. O arquivo .env + a biblioteca python-dotenv automatizam: as variáveis ficam num arquivo local (FORA do Git!) e são carregadas no início do programa.

EX 04

python-dotenv: carregando o .env 🔑

⭐⭐ médio
🎯 Objetivo

Centralizar a configuração do projeto num arquivo.

🧭 Passo a passo
  1. Instale: pip install python-dotenv (e atualize o requirements.txt!)
  2. Crie o .env com as variáveis do sistema
  3. No topo do código: load_dotenv() — e o os.environ.get passa a enxergá-las
.env
DB_HOST=localhost
DB_USER=root
DB_PASS=minha-senha-secreta
JWT_SECRET=um-segredo-bem-grande-e-aleatorio
db.py
import os
import pymysql
from dotenv import load_dotenv

load_dotenv()   # le o arquivo .env desta pasta

def conectar():
    return pymysql.connect(
        host=os.environ.get("DB_HOST", "localhost"),
        user=os.environ.get("DB_USER", "root"),
        password=os.environ.get("DB_PASS", ""),
        database="tua_caneca")
✅ Saída esperada
terminal
(o mesmo código de sempre — mas a configuração agora vive num arquivo só)
💡 Um .env por ambiente
A mágica: o MESMO código roda em qualquer lugar, mudando só o .env — na sua máquina aponta para o MariaDB local; no servidor de produção, para o banco na nuvem. Código é único, configuração é por ambiente. E o .env NUNCA vai para o Git (Semana 33) — no repositório, publica-se um .env.example com as chaves e valores falsos, como documentação.

04

debug=False e o servidor WSGI

Conceito

Duas mudanças obrigatórias para ir ao ar: desligar o debug e trocar o servidor de desenvolvimento do Flask por um servidor WSGI de verdade.

EX 06

O perigo do debug em produção 🚨

⭐⭐ médio
🎯 Objetivo

Ver com os próprios olhos o que o debug=True expõe.

🧭 Passo a passo
  1. Com debug=True, provoque um erro na API (ex.: divida por zero numa rota)
  2. Abra a rota no navegador: o Flask mostra o TRACEBACK completo — seu código-fonte, caminhos de arquivos, variáveis!
  3. Agora imagine essa tela aberta para a internet inteira...
terminal
ZeroDivisionError: division by zero
File "/home/robson/tua_caneca/api.py", line 42, in relatorio
    media = total / qtd
(... o codigo-fonte da sua aplicacao, exposto na tela ...)
🧭 Continue
  1. Em produção, SEMPRE debug=False (ou melhor: controle pelo .env!)
  2. Erros em produção devem virar um JSON genérico de erro 500 — nunca um raio-X do sistema
🔑 Ver solução

Só abra depois de tentar!

api.py (trecho)
import os
from dotenv import load_dotenv

load_dotenv()

# no fim do arquivo:
if __name__ == "__main__":
    modo_debug = os.environ.get("FLASK_DEBUG", "0") == "1"
    app.run(debug=modo_debug)

# no .env de desenvolvimento:  FLASK_DEBUG=1
# no .env de producao:         FLASK_DEBUG=0  (ou simplesmente ausente)

O debug é uma ferramenta MARAVILHOSA em desenvolvimento (recarrega sozinho, mostra erros ricos) e uma porta escancarada em produção. Controlá-lo pelo .env fecha a questão: o mesmo código, seguro em cada ambiente.

EX 07

WSGI: o motor de produção 🏭

⭐⭐ médio
🎯 Objetivo

Entender por que app.run() não vai para produção — e o que vai no lugar.

🧭 Passo a passo
  1. O servidor do app.run() avisa na inicialização: "This is a development server" — ele atende UMA requisição por vez!
  2. Produção usa um servidor WSGI: gunicorn (Linux) ou waitress (qualquer sistema)
  3. Experimente: pip install waitress e rode a API com ele
terminal
$ pip install waitress
$ waitress-serve --port=5000 api:app
INFO:waitress:Serving on http://0.0.0.0:5000
✅ Saída esperada
terminal
(a mesma API, servida por um servidor de produção multi-requisições)
💡 api:app — o endereço do app
O api:app significa "no arquivo api.py, o objeto app". O WSGI é o padrão que conecta servidores de produção a apps Python — o gunicorn com vários "workers" atende dezenas de requisições simultâneas. É a diferença entre uma bicicleta e um caminhão: o mesmo destino, capacidades muito diferentes.
05

Docker e o mapa do deploy

Conceito

Última peça conceitual: o Docker empacota app + dependências + configuração num "contêiner" que roda IGUAL em qualquer máquina — o fim definitivo do "funciona na minha máquina". Você não precisa dominá-lo hoje, mas precisa LER um Dockerfile e entender o que ele resolve.

EX 08

Lendo um Dockerfile 🐳

⭐⭐ médio
🎯 Objetivo

Decifrar a receita de um contêiner, linha por linha.

🧭 Passo a passo
  1. Leia o Dockerfile abaixo e traduza cada linha ANTES de ver a solução:
  2. Repare como ele reúne TUDO o que você aprendeu esta semana
Dockerfile
FROM python:3.12-slim

WORKDIR /app

COPY requirements.txt .
RUN pip install -r requirements.txt

COPY . .

CMD ["waitress-serve", "--port=5000", "api:app"]
🔑 Ver solução

Só abra depois de tentar!

Tradução: FROM — parte de uma imagem com o Python 3.12 já instalado; WORKDIR — trabalha na pasta /app; COPY requirements + RUN pip install — instala as dependências (a sua lista de ingredientes!); COPY . . — copia o código do projeto; CMD — o comando que roda quando o contêiner liga (o waitress do exercício anterior!). Um Dockerfile é o seu ritual de instalação, escrito como receita executável. Quem tem o contêiner não precisa instalar nada — nem Python. Ele roda igual no seu PC, no servidor, na nuvem. Por isso o Docker dominou o mundo do deploy.
