01

Relacionamentos: a alma do banco relacional

Conceito

Na Semana 30 sua tabela vendas guardava produto_id — um NÚMERO apontando para a tabela produtos. Isso é um relacionamento, e é ele que dá nome aos "bancos relacionais". A coluna que aponta para outra tabela chama-se chave estrangeira (foreign key).

Por que guardar o id e não o nome? Três motivos: se o nome do produto mudar, muda num lugar só; números ocupam menos espaço e comparam mais rápido; e o banco consegue GARANTIR que a venda aponta para um produto que existe.

EX 01

Por que produto_id e não o nome? 🤔

⭐ básico
🎯 Objetivo

Sentir na pele o problema de duplicar dados.

🧭 Passo a passo
  1. Imagine a tabela vendas guardando o NOME do produto em cada linha:
  2. a) A "caneca branca" vira "caneca branca P" — quantas linhas você teria que atualizar?
  3. b) Alguém digita "Caneca Branca" (maiúsculas) numa venda — o GROUP BY ainda agrupa certo?
  4. c) Com produto_id, os dois problemas existem?
🔑 Ver solução

Só abra depois de tentar!

a) Com o nome duplicado, TODAS as vendas antigas precisariam de UPDATE (e se esquecer uma, o relatório quebra). Com o id, muda-se o nome UMA vez na tabela produtos. b) "caneca branca" ≠ "Caneca Branca" para o GROUP BY — o relatório dividiria o mesmo produto em dois! Com o id, impossível errar. c) Não: o id é único, imutável e verificável. Regra de ouro da modelagem: cada informação vive num lugar só; as outras tabelas apenas APONTAM para ela. É o DRY (Semana 6) aplicado a dados!

EX 02

FOREIGN KEY: o contrato entre tabelas 📜

⭐⭐ médio
🎯 Objetivo

Recriar a tabela vendas com uma chave estrangeira de verdade.

🧭 Passo a passo
  1. No DBeaver, rode o CREATE abaixo — a novidade é a linha FOREIGN KEY
  2. Ela declara: "produto_id aponta para produtos(id)"
  3. Agora o banco RECUSA uma venda com produto_id que não existe!
fk.sql
USE tua_caneca;

CREATE TABLE IF NOT EXISTS vendas_v2 (
    id INT AUTO_INCREMENT PRIMARY KEY,
    produto_id INT,
    qtd INT,
    total DECIMAL(10,2),
    FOREIGN KEY (produto_id) REFERENCES produtos(id)
);
✅ Saída esperada
terminal
(tabela criada — e no DBeaver, a aba "Foreign Keys" mostra o vínculo)
💡 O banco como guardião
Tente inserir uma venda com produto_id = 9999 (que não existe): o MariaDB recusa com erro de "foreign key constraint fails". Antes, a validação era só no seu Python; agora o PRÓPRIO BANCO garante a integridade. Defesa em camadas — como a validação no servidor da Semana 23!

solucao_ex03.py
import pymysql
from db import conectar   # Semana 26

con = conectar()
cur = con.cursor()

try:
    cur.execute(
        "INSERT INTO vendas_v2 (produto_id, qtd, total) VALUES (%s, %s, %s)",
        (9999, 1, 10.0))
    con.commit()
except pymysql.err.IntegrityError:
    print("Produto inexistente — venda recusada pelo banco! 🛡️")

con.close()

O IntegrityError é o banco defendendo a consistência dos SEUS dados. Na API, capture-o e devolva 400 ou 404 — nunca deixe o erro cru vazar para o cliente.

02

INNER JOIN: cruzando as tabelas

Conceito

A tabela vendas guarda produto_id = 1... mas o relatório precisa mostrar "caneca branca"! O JOIN junta as duas tabelas na consulta, seguindo o relacionamento:

a_magica.sql
SELECT v.qtd, p.nome
FROM vendas v
JOIN produtos p ON p.id = v.produto_id

Leia: "pegue as vendas e, PARA CADA UMA, encontre o produto cujo id bate com o produto_id". O ON é a regra do encaixe. Os apelidos v e p (aliases) encurtam a escrita.

EX 04

Seu primeiro JOIN 🤝

⭐⭐ médio
🎯 Objetivo

Listar as vendas com o NOME do produto (não o id).

🧭 Passo a passo
  1. Monte o SELECT com JOIN produtos p ON p.id = v.produto_id
  2. Peça as colunas com o apelido: p.nome, v.qtd, v.total
  3. Rode no DBeaver primeiro (para VER a tabela cruzada), depois no Python
ex04_join.py
from db import conectar

con = conectar()
cur = con.cursor()

cur.execute("""
    SELECT p.nome, v.qtd, v.total
    FROM vendas v
    JOIN produtos p ON p.id = v.produto_id
""")

for nome, qtd, total in cur.fetchall():
    print(f"{nome}: {qtd} un. — R$ {total:.2f}")

con.close()
✅ Exemplo (dados variam)
terminal
caneca branca: 3 un. — R$ 75.00
caneca preta: 2 un. — R$ 55.00
caneca branca: 1 un. — R$ 25.00
💡 O dicionário virou JOIN
Lembra da Semana 8, quando você usava um dict para "traduzir" código→nome dentro de um loop? O JOIN é ISSO, feito pelo banco, em velocidade industrial. Você já tinha a intuição — agora tem a ferramenta definitiva.

🧭 Passo a passo
  1. Liste só as vendas de valor acima de R$ 50 (WHERE v.total > 50
  2. Ordene do maior para o menor total
  3. Repare: o WHERE e o ORDER BY (Semana 22) funcionam normalmente sobre o resultado cruzado
✅ Exemplo
terminal
caneca branca: 3 un. — R$ 75.00

🔑 Ver solução

Só abra depois de tentar!

solucao_ex05.py
cur.execute("""
    SELECT p.nome, v.qtd, v.total
    FROM vendas v
    JOIN produtos p ON p.id = v.produto_id
    WHERE v.total > 50
    ORDER BY v.total DESC
""")
for nome, qtd, total in cur.fetchall():
    print(f"{nome}: {qtd} un. — R$ {total:.2f}")

A ordem das cláusulas no SQL: SELECT → FROM/JOIN → WHERE → GROUP BY → ORDER BY. Decore essa sequência — ela vale para toda consulta que você escrever na vida.

03

LEFT JOIN: o que NÃO aconteceu

Conceito

O INNER JOIN (ou só JOIN) traz apenas as linhas que TÊM par nas duas tabelas. E os produtos que nunca venderam? Eles somem do resultado! O LEFT JOIN resolve: traz TODAS as linhas da tabela da esquerda e preenche com NULL onde não houver par. Perguntas de negócio valiosas ("o que está encalhado?") vivem aí.

EX 06

LEFT JOIN: todos os produtos, vendidos ou não

⭐⭐ médio
🎯 Objetivo

Ver a diferença entre INNER e LEFT na prática.

🧭 Passo a passo
  1. Rode a mesma consulta duas vezes: uma com JOIN, outra com LEFT JOIN
  2. No LEFT, produtos sem venda aparecem com qtd None (o NULL do banco chega como None no Python — Semana 6!)
ex06_left.py
cur.execute("""
    SELECT p.nome, v.qtd
    FROM produtos p
    LEFT JOIN vendas v ON v.produto_id = p.id
""")
for nome, qtd in cur.fetchall():
    situacao = f"{qtd} un." if qtd is not None else "— nunca vendido!"
    print(f"{nome}: {situacao}")
✅ Exemplo
terminal
caneca branca: 3 un.
caneca preta: 2 un.
azulejo: — nunca vendido!
💡 Esquerda de quem?
"LEFT" = a tabela escrita ANTES do JOIN (aqui, produtos). O LEFT JOIN promete: "TODAS as linhas da esquerda entram no resultado, com ou sem par". Por isso o azulejo aparece — com NULL na parte da venda. O INNER o teria escondido.
EX 07

Os encalhados: LEFT JOIN + IS NULL 🕵️

⭐⭐⭐ desafio
🎯 Objetivo

Encontrar produtos que NUNCA venderam — a consulta de detetive.

🧭 Passo a passo
  1. Parta do LEFT JOIN anterior
  2. Filtre com WHERE v.id IS NULL — sobram só as linhas SEM par
  3. Atenção: no SQL é IS NULL, nunca = NULL
✅ Exemplo
terminal
Produtos encalhados:
azulejo
💡 A pergunta invertida
O INNER JOIN responde "o que aconteceu?"; o LEFT JOIN + IS NULL responde "o que NÃO aconteceu?" — clientes que nunca compraram, produtos parados, alunos sem entrega. Perguntas negativas são ouro para o negócio, e essa é A técnica para respondê-las.
🔑 Ver solução

Só abra depois de tentar!

solucao_ex07.py
cur.execute("""
    SELECT p.nome
    FROM produtos p
    LEFT JOIN vendas v ON v.produto_id = p.id
    WHERE v.id IS NULL
""")
print("Produtos encalhados:")
for (nome,) in cur.fetchall():
    print(nome)

Repare no (nome,): fetchall devolve tuplas mesmo com uma coluna só — a vírgula desempacota (Semana 5!).

04

JOIN + GROUP BY: relatórios profissionais

Conceito

A dupla mais usada do SQL corporativo: o JOIN cruza, o GROUP BY (Semana 22) resume. Toda pergunta do tipo "total de X por Y" com dados em tabelas diferentes passa por aqui.

EX 08

Ranking com nome de verdade 🏆

⭐⭐⭐ desafio
🎯 Objetivo

O relatório da Semana 30, agora entendido linha por linha.

🧭 Passo a passo
  1. JOIN para trazer o nome + GROUP BY p.nome para agrupar
  2. Some as quantidades e o faturamento por produto
  3. Ordene pelo total vendido
ex08_ranking.py
cur.execute("""
    SELECT p.nome, SUM(v.qtd) AS unidades, SUM(v.total) AS faturamento
    FROM vendas v
    JOIN produtos p ON p.id = v.produto_id
    GROUP BY p.nome
    ORDER BY unidades DESC
""")
print("--- RANKING TUA CANECA ---")
for nome, unidades, faturamento in cur.fetchall():
    print(f"{nome}: {unidades} un. — R$ {faturamento:.2f}")
✅ Exemplo
terminal
--- RANKING TUA CANECA ---
caneca branca: 4 un. — R$ 100.00
caneca preta: 2 un. — R$ 55.00
💡 O AS batiza a coluna
O AS unidades dá um nome ao resultado da agregação — deixa a consulta legível e permite usar ORDER BY unidades. Na Semana 30 você usou essa consulta pronta no relatório da API; agora você a DOMINA peça por peça. 🎓
EX 09

Produtos com estoque baixo E vendas altas ⚠️

⭐⭐⭐ desafio
🎯 Objetivo

Uma consulta de decisão: o que repor com urgência (sem código pronto!).

🧭 Passo a passo
  1. Combine tudo: JOIN + GROUP BY + HAVING
  2. Traga produtos com estoque < 5 cujas vendas somam 2+ unidades
  3. Pesquise o HAVING: é o WHERE dos grupos (filtra DEPOIS do GROUP BY)
✅ Exemplo
terminal
Repor com urgência:
caneca branca (estoque 3, vendeu 4)
💡 WHERE vs HAVING
O WHERE filtra LINHAS antes de agrupar; o HAVING filtra GRUPOS depois de agregar. "Estoque < 5" é sobre a linha (WHERE); "vendeu 2+" é sobre a soma do grupo (HAVING). Saber onde cada filtro entra é marca de quem entende SQL de verdade.
🔑 Ver solução

Só abra depois de tentar!

solucao_ex09.py
cur.execute("""
    SELECT p.nome, p.estoque, SUM(v.qtd) AS vendidas
    FROM produtos p
    JOIN vendas v ON v.produto_id = p.id
    WHERE p.estoque < 5
    GROUP BY p.nome, p.estoque
    HAVING vendidas >= 2
""")
print("Repor com urgência:")
for nome, estoque, vendidas in cur.fetchall():
    print(f"{nome} (estoque {estoque}, vendeu {vendidas})")

Três tabelas: clientes entram em cena

Conceito

Sistemas reais têm MUITAS tabelas relacionadas. Vamos adicionar clientes e ligar: cliente → venda → produto. Um JOIN duplo responde "quem comprou o quê".

EX 10

A tabela de clientes

⭐⭐ médio
🎯 Objetivo

Criar clientes e ligá-los às vendas.

🧭 Passo a passo
  1. Crie a tabela clientes (id, nome) e adicione cliente_id às vendas (com FOREIGN KEY)
  2. Insira 2-3 clientes e registre vendas apontando para eles
clientes.sql
CREATE TABLE IF NOT EXISTS clientes (
    id INT AUTO_INCREMENT PRIMARY KEY,
    nome VARCHAR(100)
);

ALTER TABLE vendas_v2 ADD COLUMN cliente_id INT;
ALTER TABLE vendas_v2 ADD FOREIGN KEY (cliente_id) REFERENCES clientes(id);

EX 11

JOIN triplo: quem comprou o quê 🔗

⭐⭐⭐ desafio
🎯 Objetivo

Cruzar clientes, vendas e produtos numa consulta só.

🧭 Passo a passo
  1. Dois JOINs em sequência: vendas→produtos e vendas→clientes
  2. Cada JOIN tem seu próprio ON
  3. Traga: nome do cliente, nome do produto, quantidade
ex11_triplo.py
cur.execute("""
    SELECT c.nome AS cliente, p.nome AS produto, v.qtd
    FROM vendas_v2 v
    JOIN produtos p ON p.id = v.produto_id
    JOIN clientes c ON c.id = v.cliente_id
""")
for cliente, produto, qtd in cur.fetchall():
    print(f"{cliente} comprou {qtd}x {produto}")
✅ Exemplo
terminal
Ana comprou 3x caneca branca
Bruno comprou 2x caneca preta
Ana comprou 1x caneca personalizada
💡 JOINs empilham
Cada JOIN adiciona uma tabela ao cruzamento — dois, três, cinco JOINs são rotina em sistemas reais. A tabela vendas aqui é o "centro" que conecta tudo (quem + o quê + quanto). Modelagens assim, com uma tabela de eventos ligando entidades, aparecem em TODO sistema comercial.

Projeto: relatórios profissionais na API 📊

⭐⭐⭐ desafio
🎯 Objetivo

Servir os novos relatórios com JOIN pela API REST (Semanas 27-28).

🧭 Requisitos
  1. Endpoint GET /api/relatorio/ranking: o ranking por produto (JOIN + GROUP BY) em JSON
  2. Endpoint GET /api/relatorio/encalhados: produtos sem venda (LEFT JOIN + IS NULL)
  3. Endpoint GET /api/relatorio/clientes: total comprado por cliente (JOIN triplo + GROUP BY)
  4. Proteja-os com @token_required (Semana 28) — relatório é coisa interna!
✅ Exemplo
terminal
GET /api/relatorio/encalhados (com token)
-> [{"produto": "azulejo"}]
💡 Você virou analista
Uma API que serve relatórios com JOINs protegidos por autenticação — isso é ferramenta de gestão de verdade. O frontend (Semana 29) pode consumir esses endpoints e montar um painel gerencial. Cada peça que você aprendeu multiplica as anteriores. 📈
🔑 Ver solução

Só abra depois de tentar!

api_relatorios.py
@app.route("/api/relatorio/ranking")
@token_required
def relatorio_ranking(usuario_logado):
    con = conectar(); cur = con.cursor()
    cur.execute("""
        SELECT p.nome, SUM(v.qtd) AS unidades, SUM(v.total) AS faturamento
        FROM vendas v JOIN produtos p ON p.id = v.produto_id
        GROUP BY p.nome ORDER BY unidades DESC""")
    dados = [{"produto": n, "unidades": int(u), "faturamento": float(f)}
             for n, u, f in cur.fetchall()]
    con.close()
    return jsonify(dados)

@app.route("/api/relatorio/encalhados")
@token_required
def relatorio_encalhados(usuario_logado):
    con = conectar(); cur = con.cursor()
    cur.execute("""
        SELECT p.nome FROM produtos p
        LEFT JOIN vendas v ON v.produto_id = p.id
        WHERE v.id IS NULL""")
    dados = [{"produto": n} for (n,) in cur.fetchall()]
    con.close()
    return jsonify(dados)

Projeto bônus: o histórico do cliente 🧾

⭐⭐⭐ desafio
🎯 Objetivo

Um endpoint de extrato por cliente (sem código pronto!).

🧭 Roteiro
  1. GET /api/clientes/<id>/compras: todas as compras de UM cliente, com nome do produto, qtd e total
  2. JOIN duplo + WHERE pelo id do cliente (placeholder %s!)
  3. Se o cliente não existir, 404; inclua no JSON um campo com a soma total gasta
  4. Teste com requests para 2 clientes diferentes
✅ Exemplo
terminal
GET /api/clientes/1/compras ->
{"cliente": "Ana", "total_gasto": 100.0,
 "compras": [{"produto": "caneca branca", "qtd": 3, "total": 75.0}, ...]}
💡 Empurrãozinho
É o JOIN triplo do EX 11 com um WHERE c.id = %s. Para a soma, você pode usar SUM numa segunda consulta ou somar no Python (Semana 3!). Um endpoint desses alimenta a tela "minhas compras" de qualquer loja online — você sabe construir o motor por trás dela. 😉
