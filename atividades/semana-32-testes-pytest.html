01

Por que testar? (e o assert)

Conceito

Seu sistema tem banco, API, JWT, frontend... e a cada mudança, você testa TUDO de novo na mão? Clicando, olhando, conferindo? Isso não escala. Testes automatizados são programas que testam seu programa: rodam em segundos, não esquecem nenhum caso e gritam na hora que algo quebra.

A peça básica é o assert: ele afirma que algo é verdade — e explode se não for.

EX 01

Conhecendo o assert 💥

⭐ básico
🎯 Objetivo

Entender a peça fundamental de todo teste.

🧭 Passo a passo
  1. O assert condicao não faz nada se a condição for True... e levanta AssertionError se for False
  2. PREVEJA o que acontece em cada linha, depois execute:
ex01_assert.py
def calcular_total(preco, qtd):
    return preco * qtd

assert calcular_total(10, 3) == 30
print("Primeiro assert passou!")

assert calcular_total(25.0, 2) == 50.0
print("Segundo assert passou!")

assert calcular_total(10, 0) == 999   # essa afirmação é falsa!
print("Você nunca verá esta linha.")
✅ Saída esperada
terminal
Primeiro assert passou!
Segundo assert passou!
Traceback (most recent call last):
  ...
AssertionError
💡 Afirmar, não perguntar
O assert é uma AFIRMAÇÃO: "isto É verdade". Se for, silêncio (bom sinal!); se não for, erro na cara. Um teste é só um conjunto de afirmações sobre como seu código DEVE se comportar. Simples assim — e poderoso assim.
EX 02

O custo do bug tardio 🐛💸

⭐ básico
🎯 Objetivo

Entender POR QUE empresas levam testes tão a sério.

🧭 Passo a passo
  1. Reflita sobre o mesmo bug (o desconto que calcula errado) descoberto em três momentos:
  2. a) Pelo SEU teste, 10 segundos depois de escrever a função
  3. b) Pelo colega, uma semana depois, ao usar sua função no módulo dele
  4. c) Pelo CLIENTE, um mês depois, cobrado errado na loja
🔑 Ver solução

Só abra depois de tentar!

a) Custo: 2 minutos — você corrige na hora, com o contexto fresco. b) Custo: horas — o colega investiga, te aciona, vocês depuram juntos. c) Custo: enorme — cliente irritado, reembolsos, reputação, e o bug está enterrado sob um mês de mudanças. A regra da indústria: quanto mais tarde o bug aparece, mais caro ele fica (às vezes 100x). Testes automatizados puxam a descoberta para o momento mais barato: agora. É por isso que vagas pedem "experiência com testes" — é dinheiro puro.

02

pytest: o padrão do mercado

Conceito

O pytest (pip install pytest) organiza e roda seus asserts. As convenções: testes vivem em arquivos test_*.py, dentro de funções def test_*(). Aí você digita pytest no terminal e ele encontra e roda TUDO sozinho, com um relatório colorido no final.

EX 03

Seu primeiro arquivo de testes ✅

⭐⭐ médio
🎯 Objetivo

Criar e rodar uma suíte pytest de verdade.

🧭 Passo a passo
  1. Crie loja.py com a função calcular_total (com desconto de 10% acima de 100)
  2. Crie test_loja.py com funções test_* que a verificam
  3. Rode pytest no terminal (na mesma pasta)
loja.py
def calcular_total(preco, qtd):
    total = preco * qtd
    if total > 100:
        total = total * 0.9   # 10% de desconto
    return round(total, 2)
test_loja.py
from loja import calcular_total

def test_total_simples():
    assert calcular_total(10, 3) == 30

def test_desconto_acima_de_100():
    assert calcular_total(60, 2) == 108.0   # 120 - 10%

def test_sem_desconto_no_limite():
    assert calcular_total(50, 2) == 100     # 100 nao ganha desconto
✅ Saída esperada
terminal
$ pytest
========================= test session starts =========================
collected 3 items

test_loja.py ...                                                 [100%]
========================== 3 passed in 0.02s ==========================
💡 Os três pontinhos
Cada . é um teste que passou; um F seria uma falha. O pytest ACHOU seus testes sozinho (pela convenção test_) e rodou todos. A partir de agora, "rodar os testes" é um comando de 6 letras — sem desculpa para pular!
EX 04

Vendo um teste FALHAR (de propósito) 🔴

⭐⭐ médio
🎯 Objetivo

Aprender a ler o relatório de falha — a habilidade que faz o teste valer.

🧭 Passo a passo
  1. Quebre a função de propósito: mude o desconto de 0.9 para 0.8
  2. Rode pytest e LEIA a falha com calma:
terminal
$ pytest
test_loja.py .F.                                                 [100%]
============================== FAILURES ===============================
______________________ test_desconto_acima_de_100 _____________________

    def test_desconto_acima_de_100():
>       assert calcular_total(60, 2) == 108.0
E       assert 96.0 == 108.0

===================== 1 failed, 2 passed in 0.04s =====================
🧭 Continue
  1. O pytest mostra: QUAL teste falhou, QUAL linha, e os DOIS valores (esperado vs recebido)
  2. Conserte a função (volte o 0.9) e veja tudo verde de novo
💡 Vermelho é seu amigo
O teste falhando fez o trabalho dele: pegou o bug ANTES do cliente. O ciclo profissional é: mudou o código → rodou pytest → verde? entrega; vermelho? conserta. Repare que o teste que falhou aponta a linha exata e a diferença de valores — depuração de precisão cirúrgica.
03

Casos extremos: onde os bugs moram

Conceito

Bugs raramente moram no caso comum — moram nas BORDAS: zero, negativo, vazio, o limite exato. Testar bem é perguntar "e se...?": e se a quantidade for 0? E se o preço for negativo? E se o carrinho estiver vazio?

EX 05

Caçando bordas 🎯

⭐⭐⭐ desafio
🎯 Objetivo

Escrever testes para os casos que ninguém pensa (e o código quebra).

🧭 Passo a passo
  1. Para a calcular_total, escreva testes de borda: qtd 0, exatamente 100, valor gigante
  2. Alguma borda revela comportamento estranho? (qtd negativa devia ser permitida?)
  3. Se achar um comportamento errado, você achou um BUG — conserte a função e deixe o teste de guarda
✅ Saída esperada
terminal
(testes de borda passando — ou revelando decisões que a função nem tinha tomado!)
💡 O teste que faz pensar
Escrever o teste da qtd negativa te obriga a DECIDIR: deve dar erro? Deve devolver 0? Testes não só verificam código — eles expõem decisões que você nem sabia que precisava tomar. Por isso dizem que testar melhora o DESIGN do código.
🔑 Ver solução

Só abra depois de tentar!

test_bordas.py
from loja import calcular_total

def test_quantidade_zero():
    assert calcular_total(50, 0) == 0

def test_limite_exato_sem_desconto():
    assert calcular_total(100, 1) == 100    # 100 NAO ganha desconto

def test_um_centavo_acima_ganha_desconto():
    assert calcular_total(100.01, 1) == 90.01

def test_valor_grande():
    assert calcular_total(1000, 10) == 9000.0

O teste do "um centavo acima" é clássico: limites exatos (> vs >=) são o habitat favorito dos bugs. Um bom testador pensa como o bug pensa. 🕵️

04

Exceções esperadas e parametrize

Conceito

Duas ferramentas que elevam o nível: o pytest.raises testa que um erro ACONTECE quando deve (lembra do ValueError da Semana 7?), e o @pytest.mark.parametrize roda o MESMO teste com vários dados — DRY (Semana 6) nos testes.

EX 06

Testando que o erro acontece 🧨

⭐⭐⭐ desafio
🎯 Objetivo

Garantir que entradas inválidas são recusadas com exceção.

🧭 Passo a passo
  1. Faça a calcular_total levantar ValueError para preço ou qtd negativos (Semana 7: raise
  2. No teste, use o bloco with pytest.raises(ValueError): — o teste PASSA se o erro acontecer
  3. Se a função NÃO levantar o erro, o teste falha (é isso que você quer vigiar!)
test_erros.py
import pytest
from loja import calcular_total

def test_preco_negativo_recusado():
    with pytest.raises(ValueError):
        calcular_total(-10, 2)

def test_qtd_negativa_recusada():
    with pytest.raises(ValueError):
        calcular_total(10, -1)
✅ Saída esperada
terminal
2 passed in 0.02s
💡 Erro certo na hora certa
Parece contraintuitivo: um teste que passa quando dá erro?! Mas pense: recusar entrada inválida É um comportamento correto — e comportamentos corretos merecem vigilância. O pytest.raises afirma: "aqui DEVE explodir". Se um dia alguém remover a validação, este teste acusa.
🔑 Ver solução

Só abra depois de tentar!

loja.py
def calcular_total(preco, qtd):
    if preco < 0 or qtd < 0:
        raise ValueError("preco e qtd devem ser positivos")
    total = preco * qtd
    if total > 100:
        total = total * 0.9
    return round(total, 2)
EX 07

parametrize: um teste, muitos dados ♻️

⭐⭐⭐ desafio
🎯 Objetivo

Rodar o mesmo teste com uma tabela de casos.

🧭 Passo a passo
  1. Decore o teste com @pytest.mark.parametrize
  2. Passe os nomes dos parâmetros e a lista de tuplas (entrada → esperado)
  3. O pytest roda UMA vez por tupla — 5 casos = 5 testes no relatório
test_param.py
import pytest
from loja import calcular_total

@pytest.mark.parametrize("preco, qtd, esperado", [
    (10, 3, 30),
    (60, 2, 108.0),
    (50, 2, 100),
    (100.01, 1, 90.01),
    (0, 5, 0),
])
def test_calcular_total(preco, qtd, esperado):
    assert calcular_total(preco, qtd) == esperado
✅ Saída esperada
terminal
5 passed in 0.03s
💡 A tabela de verdades
Cinco testes num só, sem copiar e colar função — é a lista de tuplas da Semana 5 alimentando o teste! Adicionar um caso novo = adicionar uma linha. Times profissionais mantêm tabelas com DEZENAS de casos assim, cobrindo cada canto da função.
05

Testando a API Flask 🌐

Conceito

O grande salto: testar a sua API REST (Semanas 27-28) SEM subir servidor. O Flask traz o test_client(): um "navegador de mentira" que chama suas rotas direto na memória — GET, POST, com token, tudo. Os testes rodam em milissegundos.

EX 08

O primeiro teste de rota

⭐⭐⭐ desafio
🎯 Objetivo

Testar o GET /api/produtos com o test_client.

🧭 Passo a passo
  1. No arquivo de teste, importe o app da sua API
  2. Crie o cliente: client = app.test_client()
  3. Chame client.get("/api/produtos") e verifique status e JSON
test_api.py
from api import app   # a sua API das Semanas 27-28

def test_listar_produtos():
    client = app.test_client()
    resp = client.get("/api/produtos")

    assert resp.status_code == 200
    dados = resp.get_json()
    assert isinstance(dados, list)   # devolve uma lista?
✅ Saída esperada
terminal
1 passed in 0.15s
💡 Sem servidor, sem espera
O test_client NÃO abre porta nem precisa do app.run() — ele injeta a requisição direto no Flask. Por isso é tão rápido. O resp.get_json() é o espelho do jsonify: desfaz o JSON para você verificar com assert.
EX 09

Testando a proteção JWT 🔐

⭐⭐⭐ desafio
🎯 Objetivo

Garantir que as rotas protegidas RECUSAM sem token e ACEITAM com.

🧭 Passo a passo
  1. Teste 1: POST sem token deve dar 401 — a segurança está de pé?
  2. Teste 2: faça login pelo próprio test_client, pegue o token e crie COM o header Authorization
  3. Dois testes que vigiam sua autenticação para sempre
✅ Saída esperada
terminal
2 passed in 0.31s
💡 Testando o cadeado
O teste do 401 é dos mais valiosos do sistema: se um dia alguém REMOVER o @token_required sem querer, ele acusa na hora. Testes de segurança são o alarme do alarme. E note o fluxo do teste 2: login → token → uso — o mesmo do frontend (Semana 29), automatizado.
🔑 Ver solução

Só abra depois de tentar!

test_auth.py
from api import app

def test_criar_sem_token_da_401():
    client = app.test_client()
    resp = client.post("/api/produtos",
                       json={"nome": "x", "preco": 1, "estoque": 1})
    assert resp.status_code == 401

def test_criar_com_token_funciona():
    client = app.test_client()

    # login (usuario de teste ja cadastrado no banco)
    resp = client.post("/api/login",
                       json={"usuario": "robson", "senha": "tuacaneca123"})
    assert resp.status_code == 200
    token = resp.get_json()["token"]

    # cria com o token
    resp = client.post("/api/produtos",
                       headers={"Authorization": f"Bearer {token}"},
                       json={"nome": "caneca teste", "preco": 20, "estoque": 3})
    assert resp.status_code == 201
    assert resp.get_json()["nome"] == "caneca teste"

Dica profissional: em projetos maiores usa-se um banco SEPARADO para testes (para não sujar os dados reais). Pesquise "pytest fixtures" quando quiser dar esse passo — é o próximo nível natural.

EX 11

Projeto bônus: caça ao bug com rede de proteção 🎪

⭐⭐⭐ desafio
🎯 Objetivo

Sentir o fluxo profissional: quebrar, detectar, consertar (sem código pronto!).

🧭 Roteiro
  1. Com a suíte verde, sabote de propósito UM detalhe da API (ex.: troque o 201 por 200, ou remova uma validação)
  2. Rode pytest — quais testes acusam? A mensagem aponta o lugar certo?
  3. Conserte e veja tudo verde de novo
  4. Reflita: sem os testes, quanto tempo até esse "sabotador" ser descoberto?
💡 O jogo do sabotador
Esse exercício tem nome chique no mercado: "mutation testing" (testar os testes!). Se você sabotar algo e NENHUM teste acusar... achou um buraco na sua rede — escreva o teste que falta. Uma suíte é tão boa quanto os bugs que ela consegue pegar. 🕳️🕸️
